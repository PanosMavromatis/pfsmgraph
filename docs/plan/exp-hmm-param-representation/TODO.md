  - [x] Split the cost of each candidate into `HMMParams` construction (validation, freezing, cached properties) and the scoring that follows it: a forward pass, and a `baum_welch` re-convergence. If construction is a negligible fraction of scoring, the dense options are already decided on cost
    > **Note:** On `python`, building (new arrays + `HMMParams` + the `state_p` solve) is 0.17 ms at S=5 and 1.2 ms at S=50. Scoring is `_suggest_d` (0.66–1.82 s) plus a `baum_welch` convergence (6.5–21 s, 80–210 cycles). Within building, `HMMParams`' validation and freezing is about the same as the array operations, and the stationary solve is smaller than either.
    > **Note:** **The numpy forward pass is nearly flat in S**: 35 ms at S=5, 43 ms at S=16, 79 ms at S=50, for 100× more arcs. So on the default backend the time is per-timestep overhead over 1449 steps, not per-arc work, and an edge list, which reduces arcs, attacks the cheaper part. That weakens the edge list's case on the backend the search defaults to.
    > **Note:** **On Cython the per-arc work does start to count.** Speedup over numpy falls from 11.2× at S=5 to 4.7× at S=50 and 1.8× at S=150, where a cycle is 547 ms. So the edge list isn't ruled out at large S, but its case is kernel speed during scoring, not storage cost. Pursuing it means reopening the eight kernel files and both `FORMALIZATION.md` documents, which is goal 2's question to weigh.
    > **Note:** **`_suggest_d` always runs the numpy forward pass**, because `_data_description_length` has no `backend=`, so each of its ~20 Brent probes is a numpy pass whatever backend trains the model. At S=5 one call is 0.80 s, about 100 Cython EM cycles, and the search calls it on every accepted move. Found here by chance; it is about the cost of scoring, not how parameters are stored, and this branch does not change it.
- [x] Measure the three representations against that workload
  > **Done:** Reallocate is the baseline from goal 1. Over-allocate and slice is **not viable as `HMMParams` is built**: `_frozen` copies every input before freezing, so a view is copied at construction. The edge list's real opportunity is **per-symbol sparsity in the kernels**: a step uses 8.7–12.1% of arcs on the trained models. That sparsity lives in the host-built arc table, not in parameter storage, so storage and kernel speed are separate decisions, and a skip-zero fold was measured bit-exact with the dense one.
  - [x] Reallocate: today's frozen dense arrays, as the baseline
    > **Note:** No separate measurement needed: goal 1 is the baseline. Building a candidate by reallocating is 0.17 ms at S=5 and 1.2 ms at S=50, about 0.005% of a move.
  - [x] Over-allocate and slice: say how a view into a larger buffer interacts with ADR 0017's frozen buffers and cached properties
    > **Note:** **Settled by reading `_params.py`, not by a benchmark.** `_frozen` ends with `array = array.copy(); array.setflags(write=False)`, with a comment explaining why: `asarray` may return the caller's own array, and freezing it would mutate an object `HMMParams` doesn't own. So a view into an over-allocated buffer is copied at construction, and slicing saves no allocation. Making it save one would mean freezing a caller's buffer in place, which the comment exists to rule out, or holding a mutable buffer behind a frozen interface, which reintroduces the stored-and-stale state ADR 0017 removed.
    > **Note:** Even if it worked, the most it could save is the build: about 1 ms against a 20 s move at S=50. So it's ruled out twice, on cost and by construction.
  - [x] Edge list: what it saves at the densities learned models reach, and what reopening all eight kernel files and both `FORMALIZATION.md` contracts would cost
    > **Note:** **A forward step uses far fewer arcs than the transition density suggests.** Per-step live arcs, where `w[i, j, sym[t]] != 0`, are **8.7% on average** (4.0–16.0%) on `m001_0005_005` against 32% of transitions non-zero, and **12.1%** (6.2–12.5%) on `m008_0001_008` against 50%. An arc counts only if it can emit that step's symbol, so emission sparsity matters per step. That caps the saving at 11.5× and 8.3× of the per-arc work, which goal 1 showed dominates only on Cython at large S.
    > **Note:** **That sparsity doesn't come from how parameters are stored.** It depends on each step's symbol and lives in the arc table ADR 0020 already has the host build from the dense arrays. A kernel could iterate a per-symbol list of live arcs built on the host, with `HMMParams` unchanged. So "edge list" mixed two decisions: how parameters are stored (irrelevant to cost, per goal 1) and how kernels iterate arcs (where the saving is). The second doesn't need the first.
    > **Note:** **Skipping exact zeros keeps the fold bit-exact.** Measured over 1268 steps on both trained models: a scalar ascending fold that skips arcs with `w == 0` agrees bitwise with the dense fold at every step, including the scale factors, **0 mismatches**, while skipping 88–91% of the terms. It follows from IEEE arithmetic, `acc + 0.0 == acc` for `acc >= +0.0`, and all terms are non-negative. So a live-arc kernel wouldn't need ADR 0020's ordering contract changed, only a clause in both `FORMALIZATION.md` documents. This tested the arithmetic under a simplified recurrence, not the package kernel, so a real implementation must still be held to the reference by the existing bit-exact suites.
    > **Note:** **What each version would reopen.** A storage-level edge list changes `HMMParams`, its validation, the arc-table builder, every consumer of dense `output_p` (both description-length halves among them), and all eight kernel files. A live-arc kernel with dense storage changes the arc-table builder and the eight kernel files, plus a clause in each `FORMALIZATION.md`, and nothing in `HMMParams`. Both are `dp-compile`-gated. These are estimated from the code, not measured.
    > **Note:** A caveat on the densities: the trained fixtures are S = 5 and 8. Goal 1's large-S timings used random Dirichlet models, which are dense, so live-arc density at the S where kernel speed matters (50–150) is unmeasured. Learned topologies there are plausibly sparser, but that's a guess, not a measurement.
- [x] Decide, and record the decision where it binds
  > **Q:** What is the representation decision: keep dense frozen storage and defer live-arc kernels, keep dense storage and build live-arc kernels now, or move to edge-list storage?
  > **A:** Keep dense frozen storage, and defer live-arc kernels. Building is about 0.005% of a move, so no layout changes a move's cost. Over-allocate-and-slice can't work while `_frozen` copies its inputs. And the edge list's saving comes from how kernels iterate arcs, not from storage. The live-arc kernel is deferred because it only pays where per-arc work dominates scoring, and live-arc density at large S isn't measured.
  > **Q:** Where should the decision be recorded: `Resolved` entries in ADRs 0015 and 0017, a new ADR 0022, or a `core.md` note only?
  > **A:** `Resolved` entries in ADRs 0015 and 0017, closing the open items where each deferred this question to revision 04. No new ADR, because nothing new is decided: the existing layout is confirmed. A `core.md` note alone would leave both ADRs still saying revision 04 will decide.

ADR 0017 gains its first `Resolved` section. `DEFERRED.md` gains `## Trigger: a trained model large enough for per-arc work to dominate` for the live-arc kernel.

- [x] Land the representation split and merge will be written against, or record that nothing changes and why
  > **Done:** Nothing lands, by decision rather than omission. Goal 3 keeps `HMMParams` as it is, so split and merge are written against today's type: free functions that take an `HMMParams`, build fresh arrays, and return `HMMParams(init_state_p, transition_p, output_p, params.vocabulary)` -- the pattern `baum_welch` already uses after every M-step (`_baum_welch.py:366`). Whether a merge rejects such a move up front or lets it raise is still the merge subgoal's decision, as the master plan already says.

- [x] Port the two code-length primitives from `Code/Utility/util.lsh`
  > **Q:** How should `_comb_code_length` be computed — a vectorised difference reduced by one ascending `np.add.accumulate`, the original's interleaved scalar loop, or an O(1) `lgamma` closed form?
  > **A:** The vectorised difference, reduced by one ascending accumulate — this package's standing idiom where reduction order is contract. It is **not** bit-identical to the original's interleaving, and the docstring says so rather than implying a transliteration.
  > **Q:** The original returns `0.0` for negative input rather than erroring. Reproduce that, or raise?
  > **A:** Raise on negative, keep `m <= 1 → 0.0`. The two guards are different in kind: `m <= 1` is mathematically correct, since a composition into one part carries no information, whereas a negative size mapped to `0.0` is the *cheapest* possible code — the same failure class as the `1e100` sentinel this revision declined, a wrong answer that is also comparable.
  > **Done:** `_mdl.py` exists with `_int_code_length` and `_comb_code_length`; `tests/test_mdl.py` holds 60 tests in five sections. Full suite 1478 passed.
  - [x] `int_code_length` — Rissanen's universal prior for the integers: `log₂ 2.865` plus the iterated logarithm while the term exceeds 1. Decide the domain (it is called on state counts and on `d`, so zero and one are the cases to pin) and check the terminating condition against the original rather than against the paper
    > **Note:** **The original codes `n + 1`, not `n`.** `util.lsh:467` increments before the loop, which has no counterpart in the usual statement of Rissanen's prior and is what makes `_int_code_length(0)` finite — `log2(2.865)` alone — rather than an iterated logarithm of zero. The model description length calls this on a state count and the search starts from one state, so the small arguments are the ones that occur.
    > **Note:** **`HMMLIB-ACCOUNT.md` §8's termination rule is loose, and the generated C settles it.** §8 says the iterated logarithm runs "while the term exceeds 1"; the code guards the *value* whose logarithm is about to be taken, so a term is added exactly when the previous value exceeded 1 — which is exactly when the new term is above zero. The last term added is therefore usually below 1. Stating it as §8 does would stop one term early. `tests/test_mdl.py` pins the actual rule.
    > **Note:** Exact values are asserted with `==` only where both sides perform the *same* arithmetic. `f(1) == LOG2_C + 1.0` is exact; `f(1) - f(0) == 1.0` is **false**, at `0.9999999999999998`, because the subtraction loses the low bit. Algebraic rearrangement is not float-safe, which is the same trap `core.md` records for the Lush fixtures' attainable `5e-5` tolerance. Both errors were in the first draft.
  - [x] `comb_code_length(sum, m)` = `log₂(sum + m) + log₂ C(sum + m − 1, m − 1)`. Use a log-gamma or a log-binomial that does not overflow; `d` reaches the hundreds and `m` is `1 + n_states`, so the binomial itself is not representable
    > **Note:** **The overflow worry was already solved by the thing being ported.** The original never forms `C(sum+m-1, m-1)`; it sums `log2(sum+i) - log2(i)` term by term (`util.lsh:479-484`). So the open question was only which safe form to use here, not whether one was needed.
    > **Note:** Measured at `d = 10000` over `m` in {2, 6, 9, 13, 32, 51}: the `lgamma` closed form agrees with the ascending loop to **4e-11 bits**, and the vectorised difference agrees with the original's interleaving to **5.7e-14**. So none of the three candidates was distinguishable on fidelity, and the choice was made on idiom.
    > **Note:** Cost is not a consideration either, contrary to how the formula reads. `comb_code_length(d, 1 + n_symbols)` is multiplied by the transition count rather than summed over transitions, and both its arguments are constant across arcs — so the model description length calls this **twice per score** whatever the state count.
  - [x] Tests: exact values against hand-computed cases, monotonicity, and agreement with a `fractions`/`mpmath` reference where one is cheap
    > **Note:** 60 tests in five sections. The oracle is arithmetic rather than the original, since there is no Lush runtime here to run: powers of two where the iterated logarithm is exact, `math.comb` where the binomial is still representable, and an `lgamma` closed form sharing no code with the loop under test, at the real arguments where the binomial has 400+ digits. Monotonicity is tested separately because neither oracle asserts it, and it is the property the search leans on — a move that adds a state must pay for it.
